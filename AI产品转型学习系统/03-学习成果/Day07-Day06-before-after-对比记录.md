日期：2026-08-06
目的：把 Day06 的真实基线和 Day07 第一轮规则层小更新后的结果并排记录，方便后续复盘、学习和面试讲述。

## 这次到底改了什么

Day07 这次没有：
- 改固定 system prompt
- 改内部实现代码
- 扩新类别
- 换模型

Day07 这次只改了：
- `Day06-用户规则配置模板-v2.2.json`

具体是：
- 补强 `05 患者隐私泄漏` 的规则说明
- 明确“判断关键不是有没有具体数字，而是有没有具名患者 + 可识别/可联系到本人的信息”
- 新增 1 条非结构化 PII 示例：
  - `登记了患者王芳的家庭住址和微信号，方便日后上门回访`

所以这是一轮非常典型的：
- `只改规则层 -> 不改固定框架 -> 用同一套评测重跑`

## 对比口径

- 模型保持不变：`deepseek / deepseek-v4-flash`
- 外部完整 benchmark 保持不变：`medical_crm_compliance_eval_dataset_cn.csv`

这意味着：
- Day06 和 Day07 的分数变化，主要可以归因到规则层的这次小更新，而不是别的变量一起变了

## 怎么解释这组结果

### 1. 这轮修改是“有效但有限”的
- 有效：
  - `CSV50` 的高危 Recall 从 `45%` 提升到 `50%`
  - 报错数从 `3` 降到 `1`
- 有限：
  - 中危 Precision 没变
  - 低危误报率没变
  - MVP 子集顶层分数没变

### 2. 为什么这是合理结果
- 因为这次只改了 `05` 类的规则层表达
- 它最可能影响的是：
  - 高危类中的 `05` 相关样例
  - 少量模型输出的稳定性
- 它本来就不太可能直接修复：
  - `03` 超适应症
  - `04` PV
  - `06` 对价化讲课费
  - `09` 违规区域拜访

### 3. 为什么 MVP 子集看起来“没变”
- 因为 `run_eval.py` 的顶层指标本来就已经很好：
  - 高危 Recall `100%`
  - 误报率 `0%`
- 这次复跑时，失败详情落在 `07-v-2`
- 这提醒我们：
  - 子集分数稳定，不代表具体失败样本完全稳定
  - LLM 语义判断层仍可能有波动

如果后面面试要用一句话总结这轮 Day07，可以这样讲：

## 这轮结果还不能说明什么

- 还不能说明 `05` 类已经被彻底修好
- 还不能说明整体高危能力已经够上线
- 还不能说明 `03 / 04 / 06 / 09` 等未实现类别有了改善

所以这轮更准确的意义是：
- 证明方法链条开始闭环了
- 不是证明产品已经成熟了
