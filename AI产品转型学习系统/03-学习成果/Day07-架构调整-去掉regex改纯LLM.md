# Day07 架构调整：去掉 regex，05 类改纯 LLM 判断

日期：2026-08-06

## Day06 时的架构：为什么当时选了"正则+LLM混合"

Day04 复盘时的判断是：05 类隐私信息里，身份证号、手机号这种是结构化、格式固定的数据，用正则匹配又快又准，还不花 LLM token；而 01（商业贿赂）、07（夸大疗效）这类判断难点在语义关系（比如"讲课费"本身不违规，关键是有没有和处方量挂钩），只有 LLM 能做这种判断。"不是所有 case 都应该无脑丢给 LLM"，这在当时是一个站得住脚的产品判断，也确实体现了效率和成本意识。

## Day07 发现的真实问题

深挖 300 case benchmark 的失败样本时，`MB143` 这条 case 暴露了一个具体问题：

- 原文："记录了科室本月美罗华受药人群的 CD20 阳性率汇总统计，数据不含任何具体患者的姓名或病案号。"
- 期望：Pass（这句话明确在说"不涉及隐私"）
- 实际：被判成 05/Reject

排查后发现根因不在 LLM，而在 regex：05 类的"病案号/病历号标注"正则写的是 `病案号[:：]?\s*\S+`——冒号是**可选**的，只要"病案号"这三个字后面跟着任意一个非空白字符（哪怕只是句号"。"），就会命中。这条 case 里"...或病案号。"精确踩中了这个漏洞，而且因为正则是前置层，这个 case 根本没机会走到 LLM 那一步就被拦错了。

这个 bug 本身不难修（改成要求冒号+至少3位字母数字），已经在代码层修复。但它引出了一个更根本的问题：**这层 regex 只能由懂正则的人写、也只能由懂正则的人修**，普通配置规则的人完全看不懂、改不了、也没法自己排查这类问题。

---

## 为什么这次选择直接去掉，而不是只修 bug

用户在核对这个 bug 的过程中提出：这个项目的产品定位从一开始就是"业务人员只写自然语言规则，系统自己判断"，配置规则的人（包括用户自己）根本不需要也不应该懂 regex。如果系统内部还留着一层只有工程师能读懂、能维护的正则，这跟产品定位本身是冲突的——即使这层东西不暴露给用户直接编辑，只要它存在，任何一次调整都需要懂代码的人介入，而不是"改一下规则说明"这么简单。

修一个具体 bug只能解决这一次的问题，去掉整层 regex 才能从根上解决"这套系统里始终有一部分东西只有工程师能维护"这件事。

---

## 具体改动

- `checker.py`：删掉 `INTERNAL_STRUCTURED_DETECTORS` 和 `regex_prefilter()`，`classify()` 现在直接调用 `llm_classify()`，不再有前置匹配这一步
- `run_eval.py`：去掉了"05类可以只靠regex测、不需要API key"这条逻辑，现在所有case都需要LLM key
- `Day06-用户规则配置模板-v2.2.json`：05类的 description 和 examples 本来就是纯自然语言（身份证号/手机号/病案号的例子都是以文字描述），不需要改内容本身，只更新了 note 说明这次调整
- `eval_cases.json`：`05-gap-1` 这条 case 的 note 做了更新，去掉"regex前置层测不出来"这个过时说法（现在不管有没有具体数字串，都统一走 LLM 判断）
- 唯一保留的一处 regex：`checker.py` 里 `extract_first_json_object()` 用 regex 从 LLM 返回的文本里提取 JSON 对象——这个和"业务规则怎么匹配文本"完全无关，纯粹是解析 API 返回格式用的管道代码，不影响"配置规则的人不用碰regex"这件事

---

## 权衡：这次改动的代价是什么

去掉 regex 不是没有代价的：

- 05 类失去了"不花 token、100% 确定性匹配"的优势，结构化 PII（身份证号这种格式固定的东西）现在也要走一次 LLM 调用，速度更慢、成本更高
- 理论上多了一点被 LLM 看漏或看错的风险——虽然 05 类的规则示例已经把身份证号、手机号的具体样例写得很清楚，大概率 LLM 能稳定识别，但"大概率"终究不是"100%确定"

换来的是：

- 整个系统只有一种判断方式，不再有"这部分是规则文本、那部分是隐藏在代码里的正则"这种混合心智负担
- 配置规则的人（不管是业务同事还是没有工程背景的自己）能完整地读懂系统在做什么、为什么这么判断，不存在"看不懂的黑盒"
- 减少了一整类 bug 的来源——regex 这次已经证明了它会因为一个小疏漏（冒号可选）产生难以预料的误判，去掉之后这类问题不会再出现

---

## 对作品集/面试的价值

这不是一次"我们把之前的设计推翻了"的挫败，而是一条完整的评测驱动迭代证据链：

> 先有一个当时合理的架构判断（正则+LLM混合，图效率）→ 用真实 benchmark 跑出来一个具体失败 case（MB143）→ 顺着这个 bug 往下查，发现的不只是一行正则的疏漏，而是这层设计本身和产品定位有冲突 → 基于这个证据，做出一次有权衡、有取舍的架构调整（放弃一部分性能/成本优势，换取"系统完全可被业务语言描述和维护"）

这正是"评测发现问题 → 归因 → 做出有理有据的产品决策"这条方法论故事最完整的一次体现，比单纯说"我们做了架构选择"更有说服力，因为它带着真实的翻转过程和权衡记录。
