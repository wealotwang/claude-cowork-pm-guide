## 今天最重要的认知转变

### 1. 不是所有可识别能力都应该让用户填写
今天一个很关键的纠偏是：
- 用户配置的是规则
- 不是底层 detector

更准确地说：
- 用户可以写“患者隐私泄漏”
- 但不应该被要求去填 regex、模式、结构化 detector 类型

这带来的产品判断是：
- 结构化识别能力可以由系统内部偷偷增强
- 这样既更真实，也更有说服力

---

### 2. action 先服务 MVP，不要反过来拖复杂度
今天另一个关键校准是：
- 当前 MVP 只保留 3 个 action 就够了
- 不要为了“术语更精细”把动作体系做复杂

这个变化看起来很小，但其实是在守住一个产品边界：
- 先证明“能不能抓住风险”
- 再细化动作策略

---

### 3. 当前评测先聚焦 Recall / Precision / 漏报
我们今天明确放弃了一种容易跑偏的方向：
- 不是先去讨论 action 枚举兼不兼容
- 而是先盯住：
  - Recall
  - Precision
  - False Negative / 漏报

这让 Day06 更像真正的 MVP 验证，而不是规范打磨。

---

### 4. system prompt 和用户规则必须拆开
这是今天最核心的结构性进展。

最后达成的清晰拆法是：
- `system prompt`：固定框架
- `用户规则`：企业自己不断增删改的变量
- `内部实现`：系统内部怎么辅助识别

这个拆分的意义非常大，因为它让后面几件事都变得清楚：
- 改 prompt 时，知道是在改固定框架还是改规则
- 改规则时，不需要重写系统角色
- 补结构化能力时，不会错误地推给用户去配置

## 今天问得特别好的问题

### 问题 1
“有些东西用户填不出来，结构化识别能力我们来试试测一下可能会更有说服力。”

为什么这是个好问题：
- 它直接区分了“用户视角”和“系统实现视角”
- 它把我们从“让用户配置太多底层细节”的错误方向拉了回来

---

### 问题 2
“几个 action 你可以不用来纠正我，我目前 mvp 只需要那 3 个 action。”

为什么这是个好问题：
- 它提醒我们：当前是 MVP，不是终局产品规范
- 产品设计要服从当前阶段目标，而不是提前追求完美分类

---

### 问题 3
“评测体系里面暂时不涉及到 action 兼不兼容，评测只需要关注召回、精准、漏报就可以。”

为什么这是个好问题：
- 它帮我们把评测重点重新压回最有业务价值的指标
- 也避免了把 Day06 变成规则字典兼容性讨论

---

### 问题 4
“我们的 system prompt 和用户的自定义 prompt 应该是拆开的。”

为什么这是个好问题：
- 这是今天所有重构的出发点
- 它不是小修小补，而是直接决定系统后面怎么长
