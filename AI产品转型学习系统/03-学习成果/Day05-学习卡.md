## 今日关键校准

### 1. 不是所有判断都要交给 LLM
05类（隐私）是结构化、格式固定的信息（身份证号、手机号），正则就能可靠识别，快且不占用API调用；01/07类的判断难点在语义关系（比如"讲课费"本身不违规，关键是有没有和处方量/进院挂钩），这种才真正需要LLM。这个架构选择直接落地了 Day04 悟出的道理，也是能在面试里讲的产品判断——不是"AI能力越强越好"，而是"该用什么方法就用什么方法"。

### 2. API key 不能由我经手，demo要对这件事设计得体面
真实LLM判断需要用户自己的 Anthropic API key，这个值任何情况下都不应该被我输入、存储或上传。所以代码设计成从环境变量读取，用户在自己终端里设置；没设置时脚本要清楚报错、给出解决办法，而不是崩溃或者假装能跑。这也是一个值得记录的工程判断：demo设计要考虑"运行环境不完整时怎么优雅降级"。

### 3. 已知局限要写进代码和文档，不是藏起来
05类正则测试时特意留了一条"已知会漏掉"的case（`05-gap-1`：只提到"电话号码"但没写具体数字），用来证明我们清楚这个demo没覆盖非结构化PII识别，而不是让这个局限被意外发现。评测报告里也把"跳过/未测"和"测过但失败"分开统计，避免指标被没跑的case拉低而失真。

### 4. 不是“接了大模型”就自动变成规则判断系统
今天补上的一个重要产品认知是：LLM 只是一个能理解自然语言和上下文的判断器，本身不等于规则系统。只有当它和规则定义、示例、输出 schema、动作策略结合起来，才构成真正的“规则驱动审核”。这也是为什么我们明确拒绝把 demo 讲成“关键词匹配升级版”，而是讲成“规则 + 示例 + LLM 的语义判断”。

### 5. 关键词匹配和规则示例判断的本质差别，在于“抓词”还是“抓关系”
今天最值得保留的一句表达是：
- 关键词匹配判断的是“有没有这个词”
- 规则示例判断判断的是“这段话有没有构成某种违规关系”

这对当前 3 类规则尤其关键：
- 贿赂 / 利益输送：难点在利益交换关系
- 夸大疗效：难点在绝对化承诺和证据边界
- 超适应症：难点在说明书范围与文本表达的知识比对

### 6. Day02 的完整规则模板，Day05 要收成 demo 可配置的最小字段
前面 Day02 做的是内部完整模板（规则名称 / 规则说明 / 违规示例 / 边界示例 / 适用范围 / 动作策略），今天则明确把 demo 视角收敛成 4 个最小字段：
- 规则名称
- 规则说明
- 规则示例
- 动作策略

这个区分很重要：
- Day02 更适合内部沉淀和后续扩展
- Day05 更适合给客户做第一版规则配置表单
