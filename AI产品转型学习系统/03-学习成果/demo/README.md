# Demo：AI Compliance Check Assistant（Day05-07 最小可运行原型）

更新时间：2026-08-06（Day07 深挖 300 case 后，去掉了 regex 前置层，改为纯 LLM 判断）

## 这是什么

Day05 设计、Day06 接入 DeepSeek 跑通验证的最小 demo，Day07 进入评测驱动迭代。**当前实际生效的是 6 类风险子集**，以 `../Day06-用户规则配置模板-v2.2.json` 为准：

| 类别 | 名称 | 风险等级 | 处置动作 | 判断方式 |
|---|---|---|---|---|
| 01 | 商业贿赂与利益交换 | Critical | Reject | LLM（语义关系判断） |
| 03 | 主动超说明书 / 超适应症推广 | Critical | Reject | LLM（语义关系判断） |
| 05 | 患者隐私泄漏 | Critical | Reject | LLM（语义关系判断，Day07起不再用regex） |
| 06 | 讲课费 / 学术赞助对价化 | Medium | PassWithNotice | LLM（语义关系判断） |
| 07 | 夸大疗效与绝对化宣讲 | Medium | PassWithNotice | LLM（语义关系判断） |
| 10 | 学术表述不严谨/完全合规 | Low | Pass | LLM（兜底类别） |

Day06 把动作空间也收敛过一次：当前只有 `Reject / PassWithNotice / Pass` 三种，不再用 `Block/Warning` 这两个旧名字（历史文档里出现的 Block/Warning 已经是旧版本说法）。

## 架构：从"正则+LLM混合"到"纯LLM"

Day04/Day06 时的判断是：05类隐私信息（身份证号、手机号）格式固定，正则识别快且不花 token；01/07这类判断难点在语义关系，只有 LLM 能做。这个混合架构本身当时是个合理的产品判断。

但 Day07 深挖 300 case benchmark 的问题样本时，发现了这个架构的一个真实代价：`MB143` 这条case（"...数据不含任何具体患者的姓名或病案号。"，本该判 Pass）被误判成 05/Reject，根因不是 LLM 判断错了，而是 05 类的 regex 有个小疏漏（冒号可选），"病案号"这三个字后面只要跟着任意标点就会误触发——这个 case 根本没走到 LLM 那一步就被 regex 拦错了。

更关键的是，这条 regex 只能靠懂正则的人写和修，而这个产品从一开始的定位就是"业务人员只写自然语言规则，系统自己判断"——regex 本身就违反了这个定位。所以 Day07 决定把这层 regex 彻底去掉：01/03/05/06/07/10 六类现在**统一**由 LLM 结合规则说明+违规示例+边界示例做判断，`checker.py` 里不再有任何 regex 匹配逻辑（`extract_first_json_object` 里那行 regex 是从 LLM 返回文本里摘 JSON 用的，跟业务规则匹配无关，纯粹是解析 API 返回格式）。

代价：05 类失去了"不花 token、100% 确定性匹配"的优势，换来的是"整个系统只有一种判断方式，配置规则的人完全不用碰任何代码"。详细决策过程见 [Day07-架构调整-去掉regex改纯LLM.md](../Day07-架构调整-去掉regex改纯LLM.md)。

Day06 定下的三层拆分仍然成立，只是第三层现在是空的：
- **固定 system prompt**（`../Day06-System-Prompt-固定模板.md`）：系统角色、输入输出格式、判断原则，基本不改
- **用户规则配置**（`../Day06-用户规则配置模板-v2.2.json`）：规则说明、违规示例、边界示例、动作——这是唯一要动的文件，纯自然语言，不含任何代码/正则
- **内部实现增强**：Day07 起已清空，历史上 05 类曾有的 regex 层见 `../Day06-内部实现说明-v1.md`（保留作历史记录，不代表当前状态）

## 文件说明

- `checker.py` —— 核心引擎：`llm_classify()` 处理全部 6 类的语义判断，`classify()` 是统一入口，优先走 DeepSeek，没配置则退回 Anthropic。也可以直接当 CLI 用。
- `../Day06-用户规则配置模板-v2.2.json` —— 规则定义唯一来源（**注意：不再是本目录下的 `rules_config.json`，后者现在只是镜像/兼容文件，不是主来源**）。
- `../Day06-System-Prompt-固定模板.md` —— 固定 system prompt。
- `../Day06-内部实现说明-v1.md` —— Day06 时期内部实现层的说明文档（历史记录，regex 已在 Day07 移除）。
- `eval_cases.json` —— MVP 子集评测，约30条，覆盖违规/边界/near-miss/已知局限四种类型（`expected_action` 字段还是 Day05 时期的旧动作名，不影响跑分——`run_eval.py` 只比对类别，不比对动作名，但迟早该更新成新名字）。
- `run_eval.py` —— 跑 eval_cases.json（MVP子集），按高危类看 Recall、中低危/合规类看误报率分开算指标。Day07起去掉regex后，所有case都需要API key才能跑。
- `run_eval_csv.py` —— 跑 CSV benchmark。现在除了仓库根目录的 `medical_crm_compliance_eval_dataset_cn.csv`，也支持直接传入更大的外部 CSV（例如 Day07 的 300 case）。已支持：
  - `分类ID` 自动补零
  - 忽略或可选处理 `预期动作`
  - `--workers` 并发
  - `--progress-every` 进度输出
  - `--results-out` 逐条结果落盘

## 怎么跑

```bash
export DEEPSEEK_API_KEY=”你的key”   # Day06起默认优先走DeepSeek；没设置也支持ANTHROPIC_API_KEY兜底

cd 03-学习成果/demo
python3 checker.py “这个月表现不错，给你包个红包”   # 单条测试
python3 run_eval.py                                # MVP子集评测
python3 run_eval_csv.py                             # 完整CSV50压力测试
```

Day07 起必须设置 LLM key 才能跑：去掉 regex 前置层后，05 类也和其他类一样需要 LLM 判断，没有 key 的话所有 case 都会被标记为"跳过"，而不是报错崩溃。

## 已知局限（demo 阶段主动收敛，不是遗漏）

- 05类的非结构化隐私识别（"具名患者+联系方式/住址/病历信息"）完全依赖 LLM 对规则示例的泛化能力，不再有 regex 兜底。MVP子集里曾经的已知局限`05-gap-1`（具名患者+文字描述的联系方式、无具体数字）Day07重跑已经稳定通过，但这只证明了LLM能泛化到这一种非结构化模式，不代表所有非结构化PII场景都已覆盖
- 当前虽然已经补入 `03` 与 `06`，但 `02 / 04 / 08 / 09` 仍未形成独立稳定的分类能力
- `06` 当前的主要难点不是能不能识别风险，而是容易被更粗粒度地吸到 `01 商业贿赂`（Day07已针对性补充了01/06边界说明，待重新验证效果）
- 输出稳定性：300 case 跑分里曾有约9%的case因LLM返回空内容/截断JSON而报错。验证MB143时实测抓到一次真实截断（`max_tokens=300`太紧），调到600之后重跑同一条又稳定复现了一次截断——说明单靠加大token预算不够，这类问题本质是非必现的，已经在`llm_classify()`里加了失败重试一次的逻辑（内部实现层，用户不需要关心），`run_eval.py`也补了报错详情打印方便定位是哪条case、什么原因。还没用300 case验证这个组合拳能收敛多少
- 目前是纯文本分类，没有接入 RAG 做依据引用（规则4.5的能力扩展留到demo稳定之后再加）
