## 当前系统内部执行流程
1. 接收一条 CRM 拜访记录文本
2. 先尝试系统内部的结构化识别增强
3. 如果没有命中，再把“固定 system prompt + 当前启用规则”一起送给 LLM
4. LLM 返回固定 JSON 结构
5. runner 再把实际结果与 golden label 做比对

---

## 当前已存在的内部增强

### A. 05 类结构化 PII 识别增强
当前系统内部会优先对 05 类做结构化识别增强，包括：
- 身份证号
- 手机号
- 病历号 / 病案号标注

特点：
- 这是系统内部能力
- 不是让用户填写 regex
- 用户只需要写“患者隐私泄漏”这条规则
- 系统内部再决定先用什么技术辅助判断

当前限制：
- 更擅长识别结构化号码串
- 对姓名、住址、病历照片、掩码号码、非结构化隐私表达还不够强

---

## 当前没有做成“用户配置项”的东西
下面这些能力，不应该要求用户填写：
- regex pattern
- detector 类型
- LLM provider
- prompt 组装方式
- 输出解析方式

原因：
- 这些都是系统内部实现细节
- 会给用户造成额外理解负担
- 也不符合“用户只描述规则，系统自己决定怎么识别”的产品定位

---

## 当前 runtime 的真实边界

### 已实现得比较稳的
- 01 商业贿赂与利益交换
- 07 夸大疗效与绝对化宣讲
- 10 默认 Pass / 合规兜底
- 05 的结构化 PII 子集

### 当前还没真正实现的
- 02 非法获取统方数据
- 03 主动超说明书 / 超适应症推广
- 04 隐瞒 / 延迟报告不良反应
- 06 讲课费 / 学术赞助对价化
- 08 无证据竞品对比与贬低
- 09 规避备案 / 违规区域拜访

这意味着：
- 这些类在完整 CSV50 里跑不出来，不是“用户规则写得不够好”
- 而是当前内部能力本来就没覆盖

---

## 当前评测时最该关注什么
当前阶段先关注：
- Recall
- Precision
- False Negative / 漏报

当前阶段先不把重点放在：
- action 名称细节是否足够精细
- detector 是否对外暴露

原因：
- 当前还是 MVP
- 先证明“能不能抓住风险”
- 再细化动作策略
