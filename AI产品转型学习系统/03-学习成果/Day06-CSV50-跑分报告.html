规则类别 当前是否已实现 动作 怎么配置 当前限制

2. 一条真实 dataset 进来之后，系统会跑什么流程

当前执行逻辑来自 demo/checker.py，但概念上已经拆成“固定框架 + 用户规则 + 内部增强”三层。
步骤 1
读取输入文本
从 CRM 拜访记录里拿到一条自由文本。
步骤 2
先走系统内部结构化识别增强
当前内部只对 05 做增强；如果命中身份证号、手机号、病案号等结构化 PII，直接判 05 / Reject。
步骤 3
没命中正则，再走 LLM
系统把“固定 system prompt + 当前启用的用户规则配置”一起发给 LLM。
步骤 4
DeepSeek 返回 JSON
期望返回 matched_rule_id / risk_level / action / rationale。
步骤 5
和 golden label 对比
由 runner 把实际结果和 dataset 里的预期分类、预期动作做对比。
步骤 6
汇总成 metrics
按 Release Gate 和 Diagnostic 两层输出结果。

3. 这次 evals 是怎么设计的，来源文件是什么

  • 完整 benchmark 文件：medical_crm_compliance_eval_dataset_cn.csv
  • 它包含完整 10 类、50 条中文 benchmark case，是“完整产品框架”的测试集。
  • 完整框架定义来源： CRM-Compliance-Eval框架说明.md 与 CRM-Compliance-Eval-框架-v2.html
  • 当前 demo 子集评测文件是： demo/eval_cases.json
  • 所以你现在其实有两套 evals：
    • MVP 子集评测：回答“当前已实现范围内跑得怎样”
    • CSV50 完整评测：回答“当前 MVP 距离完整 10 类产品还差多少”

4. 这次结果最重要的前提

  • 这次评测不是“当前 demo 的最佳分数”，而是“当前 demo 在完整 10 类框架下的真实压力测试结果”。
  • 因此它天然会暴露一个事实：当前 demo 只实现了 4 类能力，面对 02 / 03 / 04 / 06 / 08 / 09 这些未实现类别，成绩一定会显著下滑。
  • 这不是坏事，反而能把“当前 MVP 的边界”讲清楚。

5. Metrics 来源

  • Release Gate 定义来源： CRM-Compliance-Eval框架说明.md 与 CRM-Compliance-Eval-框架-v2.html
  • 其中明确给出了 3 个上线门槛： 高危召回率 100%、 中危精准度 ≥ 90%、 低危误报率 ≤ 10%
  • Release Metrics 与 Diagnostic Metrics 的区分解释来源： Day03-AI-Compliance-Eval-设计学习报告.md 与 可视化版

6. 这次怎么解释这些 Metrics

指标 这次采用的解释口径 为什么这样算
高危类 Recall（01-05） 所有 Critical case 里，有多少最终仍然被系统识别成 Critical 当前阶段先看高危有没有被抓住，不先被动作枚举绑定；这样更贴近现在的 MVP 评测重点。
中危类 Precision（06-09） 所有被系统识别成 Medium 的 case 中，有多少本来就真的是 Medium 当前阶段先看中危判断靠不靠谱，避免把未实现类别都压成一个“差不多的中危”。
低危误报率 所有 Low / 正常样本里，有多少没有被判成 Low 这个指标反映正常内容有没有被误伤；当前我们先从风险等级层看，而不是从动作细节层看。
Diagnostic 指标 Overall Exact Action Accuracy、Overall Exact Category Accuracy 等 这些更适合解释“错在哪”，而不是直接决定能不能上线。

9. 结果解析：为什么有些数据没测出来或没打对

失败类型 代表类别 / 样例 更准确的原因
规则缺失 02 / 03 / 04 / 06 / 09 这些类在完整框架里有，但当前 demo 规则配置里没真正实现，所以不是“没侦测到一个词”，而是“系统本来就没有这条规则能力”。
侦测能力不足 05 类部分 case 当前 05 主要靠结构化 PII 正则，遇到掩码号码、姓名、住址、病历照片、非结构化隐私表达时，能力不够。
动作相似但类别塌缩 08 → 07 有些样例动作上看似对了，但其实只是被塌缩到了另一个同样输出 Warning 的类别，不代表规则真正存在。
运行稳定性问题 007 / 008 / 015 不是规则定义本身，而是模型返回了空内容、截断 JSON 或超时后统一记错，说明输出稳定性还要继续补。

10. 按类别看，问题在哪里

类别 当前结果 怎么解读
01 Category 100% / Action 100% 这是当前 demo 已实现类别，表现稳定。
02 Category 0% / Action 25% 当前 demo 没有“统方数据”这类专门规则，部分 case 被放过，还有 1 条报错。
03 Category 0% / Action 0% 超适应症大多被压成 10/Pass，说明当前 demo 还没有这条高危规则能力。
04 Category 0% / Action 0% PV 隐瞒被错误归为 07/PassWithNotice 或直接报错，说明当前 prompt 没有专门覆盖 PV 风险。
05 Category 100% / Action 100% CSV50 这轮 05 四条都被抓到，但当前能力仍主要依赖结构化增强，非结构化 PII 仍然是下一步最值得补的方向。
06 Category 0% / Action 0% 讲课费对价化属于我们框架里明确存在、但 demo 还没实现的类。
07 Category 100% / Action 100% 这是当前 demo 已实现类别，表现稳定。
08 Category 0% / Action 100% 当前虽然把 08 都打成中危，风险等级上“看起来对了”，但类别上其实被塌缩到了 07，说明只是等级相似，不代表规则真的实现了。
09 Category 0% / Action 0% 当前 demo 没有这条专门规则，规避备案类都没被正确处理。
10 Category 100% / Action 100% 当前低危/正常样本这轮表现稳定，也说明 risk-level 口径下的低危误报已经收敛到 0%。

12. 关键结论

  • 如果用当前 demo 自己的 4 类子集评测，它能拿到不错的分数；但一旦换成完整 10 类、50 条 benchmark，就会立刻暴露“能力范围不够”的问题。
  • 这说明上一轮 30 条评测更适合证明“MVP 在自己实现范围内能跑”，而这轮 50 条更适合证明“当前 MVP 还不能代表完整产品能力”。
  • 最值得保留的不是“分低了”，而是现在我们能非常清楚地说出：差距主要来自 未实现类别、05 非结构化 PII 能力不足、以及 部分 LLM 输出稳定性。
