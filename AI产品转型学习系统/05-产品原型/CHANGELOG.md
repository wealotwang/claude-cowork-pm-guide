# 产品改动记录（CHANGELOG）

这份文件只记录一件事：**产品本身（demo/规则/代码）在什么时候、因为学了什么/发现了什么、改了什么、得到了什么结果**。

跟 `02-学习计划/01-计划变更记录.md`不是一回事——那份记录的是"学习计划"怎么变，这份记录的是"产品"怎么变。跟每天的 `DayXX-学习卡.md` 也不是一回事——学习卡记录的是当天完整的学习过程和心得，这里只摘产品改动这一条线，按时间倒序排列，方便面试前快速过一遍"这个系统是怎么一步步长出来的"。

格式固定：**日期 → 因为什么 → 改了什么 → 结果如何**。

## 2026-08-06（Day07 第二轮）：修复两个真实bug，去掉regex改纯LLM架构

**因为什么**：用300 case逐条核对失败样本根因，发现两个范围内真实问题：`MB143`（05类误伤群体汇总统计数据）和`MB197`（06类学术费用对价化被误判成01商业贿赂）。排查`MB143`时发现根因不是LLM判断问题，而是`checker.py`里05类的regex有疏漏（冒号可选，导致"...或病案号。"这种否定句也被误命中）。用户进一步指出：配置规则的人理解不了regex，这跟"业务人员只写自然语言规则"的产品定位冲突。

**改了什么**：
- 去掉05类的regex前置层，01/03/05/06/07/10六类统一改为纯LLM判断
- 修了两个真实bug：05类description补充"群体汇总统计不算违规"的澄清+边界示例；01/06类都补充了互相引用的边界说明（区分"私下现金"vs"公司正规申请流程的费用"）
- `llm_classify()`加了失败重试一次的逻辑，`LLM_MAX_TOKENS`从300调到600（实测抓到过真实的JSON截断）
- 更新了一条历史eval case（`07-v-2`）：Day05时03类还不存在只能塞进07，现在03类已独立实现，期望值同步更新为03

**结果如何**：MVP子集`run_eval.py` 30/30全部通过，0失败0报错，高危Recall 100%(7/7)、误报率0%(0/16)，包括曾经的已知局限`05-gap-1`这次也稳定通过了。还没用CSV50/300 case大样本重新验证。
