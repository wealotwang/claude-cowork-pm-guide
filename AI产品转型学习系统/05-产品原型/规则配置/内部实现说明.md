## 当前系统内部执行流程（Day07起）
1. 接收一条 CRM 拜访记录文本
2. 把"固定 system prompt + 当前启用规则"一起送给 LLM（优先 DeepSeek，没配置则退回 Anthropic）
3. LLM 返回固定 JSON 结构；如果解析失败（空内容/截断），自动重试一次
4. 结果和 golden label（如果有）做比对

**Day06时这里还有一步"先走正则前置层"，Day07已经去掉了**——原因和过程见 `../CHANGELOG.md`。

## 当前内部增强：只剩输出稳定性这一层
- `LLM_MAX_TOKENS` 从300调到600（Day07实测抓到过响应被截断的情况）
- 调用失败（JSON解析不出来）时自动重试一次
- 这两项都是纯粹的"保证调用能稳定拿到结果"，不涉及任何业务规则判断，用户不需要关心

---

## 当前没有做成"用户配置项"的东西
下面这些能力，不应该要求用户填写：
- LLM provider（DeepSeek/Anthropic 由环境变量自动选择）
- prompt 组装方式
- 输出解析方式
- 重试次数/token预算这类调用参数

原因：
- 这些都是系统内部实现细节
- 会给用户造成额外理解负担
- 也不符合"用户只描述规则，系统自己决定怎么识别"的产品定位——这也是Day07去掉regex的根本原因

## 当前 runtime 的真实边界

### 已实现得比较稳的（Day07第二轮验证：MVP子集30/30全过）
- 01 商业贿赂与利益交换
- 03 主动超说明书/超适应症推广
- 05 患者隐私泄漏（含非结构化场景）
- 06 讲课费/学术赞助对价化
- 07 夸大疗效与绝对化宣讲
- 10 默认 Pass/合规兜底

### 当前还没真正实现的
- 02 非法获取统方数据
- 04 隐瞒/延迟报告不良反应
- 08 无证据竞品对比与贬低
- 09 规避备案/违规区域拜访

这意味着：这4类在大样本benchmark（CSV50/300 case）里跑不出来，不是"规则写得不够好"，而是内部能力本来就没覆盖，是已知的、主动收敛的范围，不是遗漏。

---

## 当前评测时最该关注什么
先看：Recall / Precision / False Negative（漏报）
不先陷入：action细节是否足够精细、detector是否对外暴露

原因：先证明"能不能抓住风险"，再细化动作策略——这是从Day06就定下来、一直没变的MVP纪律。
