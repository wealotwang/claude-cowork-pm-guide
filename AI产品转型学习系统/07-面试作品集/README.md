# AI Compliance Check Assistant

一个面向医药CRM场景的AI辅助合规审核系统。这份README是面试作品集用的项目说明，整合自Day01-Day09的完整学习与迭代记录，原始过程见`03-学习成果/`各Day学习卡，产品当前状态见`05-产品原型/`。

> **重要声明**：这是基于行业实际业务理解、独立复刻/设计的**学习型项目**，用于AI产品经理岗位的求职作品集，不是Veeva或任何公司真实上线的产品。项目的起点是我在Veeva工作期间对医药合规审核场景的观察和思考，但完整的方案设计、架构决策、代码实现、评测迭代都是我个人在这之后独立完成的。

---

## 1. 一句话定位

面向医药CRM拜访场景的AI辅助合规审核工具：企业用自然语言规则+示例配置审核标准（不用写代码、不用懂正则表达式），系统据此判断一段拜访记录文本是否违规，并给出"拒绝/通过"的处置建议和可追溯的判断依据。

## 2. 为什么做这个项目

我在Veeva做产品经理，Veeva自家的Vault PromoMats/MedComms这条产品线本质上就是给医药企业做营销物料的MLR（医学-法务-监管）合规审核。我一直在想：这类审核工作高度依赖人工按条文逐条比对，效率低、一致性也依赖审核人员的经验，而这正是LLM语义理解能力可以介入的场景——尤其是CRM里销售代表的拜访记录，往往是最容易被忽略、但风险并不小的一类内容（不像正式宣传物料那样会经过多轮审批）。

这个项目就是把这个想法做成一个真正能跑起来、能评测、能迭代的小产品，用来验证"自然语言规则配置 + LLM语义判断"这条路径在合规审核场景里到底行不行得通、坑在哪里、怎么解决。

## 3. 系统设计

### 3.1 三层架构

系统拆成三层，互相解耦：

- **固定System Prompt**：定义"怎么判断"和"怎么输出"，不写死任何具体业务规则，规则怎么增删都不需要改这一层
- **用户规则配置**（`rules_config.json`）：企业自己维护的规则说明、违规示例、边界示例、风险等级、处置动作，全部用自然语言写，不涉及代码或正则表达式
- **内部实现**（`checker.py`）：负责调用LLM、组装prompt、解析返回结果，对用户不可见

这个拆分的价值在于：业务方（合规团队）只需要维护中间那一层的自然语言规则，不需要理解任何技术实现细节，规则的增删改查完全独立于系统改动。

### 3.2 判断方式：从"正则+LLM混合"到"纯LLM语义判断"

最早的版本（Day05）是正则前置+LLM判断的混合架构，理由是效率——正则不花token、100%确定性匹配。但Day07排查一条真实失败case（`MB143`，一段"不含任何患者姓名或病案号"的合规群体统计数据，被正则误判成隐私违规）时发现，根因是正则规则本身有漏洞，而且这层正则完全不透明——连维护规则的业务人员自己都看不懂、改不了。这跟项目"业务人员只写自然语言规则"的定位是冲突的。于是做了一次架构调整：**去掉正则前置层，全部改成纯LLM语义判断**，用泛化能力换掉了正则的"确定性匹配"优势。改完后MVP子集30条全部通过，包括之前正则处理不了的非结构化隐私case。

### 3.3 规则taxonomy：从10类到4类的一次重构

项目最早参照一份行业调研材料，设计了一套完整的10类风险分类（01-10），demo阶段只实现了其中6类。Day08用真实API key跑完300条压力测试后，从81条真实误判里挑出两条最严重的漏判case（`MB005`：科室团建餐费和用量指标挂钩；`MB251`：赞助书号换独家处方权）深挖根因，发现问题不是模型判断能力，而是**规则taxonomy本身有设计缺陷**：当时的"商业贿赂"（01）和"讲课费/学术赞助对价化"（06）是两个独立类别，区分标准是"这笔钱有没有走正规审批流程"——这个标准本身就是漏洞，因为它把判断依据错误地绑定在"表面形式"上，而不是"这个好处有没有被当成换处方的条件"这个实质问题上。系统性检查后发现类似的类别重叠问题在别处也存在（07类的规则文本原封不动照抄了04/08两个未实现类别的定义）。

这不是靠改prompt措辞能解决的问题，于是做了一次taxonomy重构：**把10类扁平化重组成4个互斥的业务大类**，不保留"大类+子类"的两层结构（两层结构里子类之间照样可能打架）：

| 新类别 | 名称 | 说明 |
|---|---|---|
| 01 | 商业贿赂和不良利益输送 | 合并原01（商业贿赂）+原06（讲课费/学术赞助对价化），判断标准改为"好处有没有被当成换处方的条件"，不再看走没走流程 |
| 02 | PV和药品安全 | 对应原04，抓的是代表有没有认真对待患者反馈的不良反应 |
| 03 | 患者数据、医生数据与患者隐私 | 合并原05（隐私泄露）+原02（违规统方），本质都是"数据处理方式不当" |
| 04 | Off-label推广与药物夸大疗效 | 合并原03（超适应症推广）+原07（夸大疗效）+原08（竞品贬低），统一升级为最严格等级 |
| 10 | 完全合规（Pass基线） | 未触发以上四类的默认通过 |

全部4个业务大类统一处置为**Critical/Reject**，不再保留Medium/PassWithNotice这个中间层级——这个中间层正是之前漏洞发生的地方。`09`（规避备案/违规区域拜访）和"角色越界"这两类明确列为未来工作，当前demo范围主动收敛掉，不是遗漏。

## 4. 评测方法论

### 4.1 Release Gate指标优先于Diagnostic指标

评测分两层：Release Gate指标（决定这套规则能不能用）和Diagnostic指标（帮助定位具体哪里弱）。核心是**召回率的优先级明显高于精准率**——这是业务性质决定的：漏掉一条真实的商业贿赂或者隐瞒的药物不良反应，代价远比多看一眼正常内容高得多。具体看三个数字：高危召回率、误报率，加一份原始混淆矩阵，防止被单一百分比误导。

召回率100%不是无脑追求的目标——把所有case都判Reject就能拿到100%召回率，代价是精准率崩掉、系统变得没法用。两个数字必须一起看。

### 4.2 数据集

评测数据集不是自己拍脑袋编几条应付，用的是几百条规模的样本，主要有：`300case-简化二分类版`（300条，只区分Critical/Reject vs Low/Pass的简化版）和`300case-新4类taxonomy重标注`（297条，机械改标出的、带完整新taxonomy分类标签的版本，供按类别拆解分析用）。同时也很清楚这些数据集本身可能存在标注质量问题（见第6节局限）。

## 5. 迭代过程与结果

| 节点 | 变化 | 结果 |
|---|---|---|
| Day05 | 写出第一版正则+LLM混合demo | 正则部分实测通过，LLM部分因无API key优雅跳过 |
| Day07（一） | 统一6类规则口径，补充05类边界示例 | CSV50高危召回率45%→50%；300case高危召回率87%、中危精准率96%、低危误报率5% |
| Day07（二） | 排查真实bug，去掉正则前置层改纯LLM | MVP子集30/30全部通过，包括此前的已知局限也解决了 |
| Day08 | 深挖MB005/MB251根因，10类taxonomy重组为4类业务大类 | 新规则JSON校验通过，系统组装和分类逻辑跑通（mock验证） |
| Day09 | 两轮真实API跑分验证新taxonomy | 第一轮：召回率95.6%/98%（两种口径）、精准率100%（294/300成功，6条报错）；第二轮：召回率98.5%、精准率100%（300/300全部成功，0报错） |

两轮跑分结果高度一致：稳定漏掉的3条case（`MB219`/`MB247`/`MB267`）经交叉验证，全部对应明确推迟未实现的09类（规避备案/违规区域拜访），不是当前4类规则的bug，反而验证了"09类先不做"这个范围收敛决策是合理的。

## 6. 诚实的已知局限

不回避问题，这是这个项目方法论的一部分：

- **09类（规避备案/违规区域拜访）和"角色越界"明确未实现**，是主动收敛的范围，不是遗漏
- **数据集标注质量没有做过正式的多人一致性校验**，现有数据集（Gemini生成、自己手写、机械改标）都是合成数据，不是真实生产失败案例，目前只做过抽样人工复核，行业标准做法（多标注人+一致性校验）还没有落地
- **真实验证只有两轮**，虽然结果高度一致（同样的3条case稳定漏掉），但两轮不足以完全排除运气成分，尤其精准率两轮都是100%，值得再跑几轮确认稳定性
- **CSV50、200case两份旧数据集还没做机械改标**，仍然是旧taxonomy编号，跑新规则时类别层面的准确率会失真，只有Release Gate层面的指标是准的
- **一条case（`MB296`，涉及"帮医生关联生意导流大额销售"）两轮结果不一致**，判断是这条case本身边界模糊，还没有定论
- **系统偶发报错**（网络超时、LLM返回内容被截断成非法JSON），已有失败重试一次的机制缓解，但没有根治，第一轮6条报错、第二轮0条报错，说明这更多是网络层偶发问题而非系统性缺陷
- **只处理文本输入**，识别不了拜访记录附件里的图片/扫描件是否包含未打码的患者信息
- **用LLM as a judge验证过一次"漏判是不是模型编理由/瞎推理"，结论是否定的**：抽样18条历史结果（含3条稳定漏判case+15条正确case做对照），让另一个模型（Claude）专门审查AI给出的判断理由是否忠实于原文、逻辑是否自洽，结果18/18全部通过——3条漏判case的理由本身没有编造信息、逻辑也站得住，问题100%出在规则范围没覆盖到"规避医院核查/备案"这类违规，不是模型推理能力的问题。这也顺带暴露了一个新发现：这类违规天然依赖代表自己如实记录，检测能力有结构性上限，即使补了规则也不会像其他4类那样召回率高（详见`05-产品原型/评估实验/`）

## 7. 竞品/行业对比

完整调研见`06-竞品调研/`。核心结论：

- **Gong.io的"Question-Based Smart Trackers"**（自然语言定义规则，零代码生效）验证了本项目"不用正则、纯自然语言规则配置"这个架构方向，Gong做到这个规模是5亿美元ARR、70亿+估值的公司，说明这不是自说自话的设计选择
- **Pepper Flow的"已核准声明矩阵（Claims Matrix）"**是04类规则的一个进阶方向：不让LLM凭空判断"这算不算夸大疗效"，而是先由医学/合规部门整理出结构化的"已核准话术库"，LLM只负责做匹配和偏差度计算，能显著降低LLM自由裁量带来的不稳定性
- **Observe.AI的"漏项检测（Omission Detection）"**指出了当前4大类完全没覆盖的一个盲区：现有规则全部是"抓住了不该说的话"，没有一类是"该说的没说"（比如该有的不良反应上报提示没写）

## 8. 未来方向

- 补齐09类（规避核查/备案），但不是简单加一条规则了事：这类违规靠"读CRM文本"这个信号源天然检测能力有限（代表主动规避监管时，不太会如实把"我怎么躲开核查"写进自己的工作记录里），所以计划是加成一个**低置信度诊断项**而不是硬性Reject——命中了标"疑似规避核查，建议人工复核"，同时在产品文档里明确写清楚这类风险的检测上限，建议配合门禁/备案系统等其他控制手段，不单独依赖这个工具兜底。配套要想清楚的是**责任边界**：AI系统的责任范围等于它明确写清楚要覆盖的规则范围，没写进范围的风险，责任还是落在原有机制上（人工审核、门禁备案），AI没有让这部分责任消失，真正会出问题的是"范围说明写得含糊、业务方误以为AI覆盖了实际没覆盖的东西"——所以"讲清楚覆盖边界"本身就是这项工作的一部分，不只是加规则那么简单
- "角色越界"这个类别同样明确推迟
- 04类接入结构化的"已核准话术库"做匹配基准，减少LLM自由裁量的不稳定性（借鉴Pepper Flow）
- 新增"漏项检测"能力，不只抓错误内容，也抓缺失的必填合规项（借鉴Observe.AI）
- CSV50、200case两份数据集补齐机械改标
- 数据集标注质量：引入抽样人工复核+标注错误率跟踪的常态化机制
- ~~多模型验证~~**已完成（2026-08-14）**：抽样60条分层样本，换Claude独立判断（不参考DeepSeek已有结果），59/60与DeepSeek判断完全一致，唯一分歧点是同一个已知taxonomy缺口case（MB219），召回率97.6%/精准率100%，跟DeepSeek全量300条的95.6%~98.5%区间高度吻合，说明规则设计不是只对DeepSeek有效，详见`05-产品原型/评估实验/`
- 多跑几轮同一数据集，确认当前召回率/精准率的稳定性不是单次运气
